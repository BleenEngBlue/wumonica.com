Tax Reconciliation Workbench

Designing reliable AI a finance reviewer can trust.

The problem

Tax teams reconcile ledgers across jurisdictions, from US sales tax to EU e-invoicing. Errors are costly, and a reviewer cannot sign off on something an AI “just decided.” The question: how do you use AI here without losing the reviewer’s trust?

The result

  • 100% recall, 1.0 precision, zero false positives against seeded ground truth: 21 seeded errors across 6 exception classes in the synthetic run, and 11 planted errors in the connector run.
  • One screen for the reviewer: the exception, the explanation, the proposed action, approve or override.
  • Every decision is logged with reviewer, timestamp, and reason, and exports as an audit trail.
  • A new country is one JSON entry and zero code changes.

Key design decisions

  1. The reviewer’s screen came first, and it set the data model. I cut the product to the one screen a reviewer needs. What that screen must show decided what each record had to contain.
  2. Jurisdictions are configuration, not code. Every source had to look the same on that screen, so a declarative connector layer turns native feeds (semicolon CSVs, comma decimals, nested-JSON e-invoice statuses) into one canonical model. The connectors feature took 4 hours and shipped with zero regressions.
  3. AI at the edges, never the core. A rules engine finds every exception in 6 classes: rate, arithmetic, duplicate invoice, e-invoice linkage, orphan e-report, and return tie-out. GPT-4.1 Mini only explains each one and proposes a disposition. It never decides what is wrong and never assigns severity.
  4. Humans at the point of consequence. Approve or override is always the reviewer’s call. Filing gates hold a return while critical or high exceptions are undecided.
  5. Visible provenance. Every AI output is schema-constrained and labeled with how it was produced.
  6. Safe by default. LLM mode is opt-in and needs both an API key and an explicit flag, so no data leaves without a deliberate choice.
  7. Quality is measured, not claimed. An eval panel scores every run against seeded errors: recall, precision, and unexplained flags.

How it earns trust: reliability and availability

  • It works without the AI. Offline mode is the default, so an API outage cannot stop a review.
  • Same input, same result. Detection is deterministic, so every finding is reproducible and auditable.
  • Access is gated. The Hugging Face deployment requires sign-in, and the signed-in username is written into every decision-log row.
  • Security-checked. Scanned with Bandit and pip-audit, and hardened through repeated Claude-assisted security reviews before and after launch.
  • Storage is an interface. It runs without a database today and can connect to whatever store a team already uses.

How it fails safely

  • If the AI is unavailable: deterministic explainer templates take over, with visible confidence scores and no network calls.
  • If the AI returns something unexpected: anything that fails the schema falls back to a template, and the label shows which one the reviewer is reading.
  • If the reviewer disagrees: they override, and the decision is logged with their identity and the time.
  • If exceptions are unresolved: filing gates block release of the return.
  • If input is risky: inputs are clamped server-side, and audit exports are protected against spreadsheet formula injection.
  • How I know it works: every run is scored against seeded errors for recall, precision, and unexplained flags.

What I would do next

  • Test the review flow with real reviewers. I have not run formal user research on it.
  • Add keyboard shortcuts for high-volume queues.
  • Wire the evals into a release gate.

Skills shown

Trustworthy AI interface design, human-in-the-loop review, configuration-driven architecture, audit trails, reliability and fallback design, evals, and fast prototyping in code.

All data is synthetic. No PII and no real financial data. This is a prototype and personal portfolio project, not a production system.
